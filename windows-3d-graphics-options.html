Windows 3D Graphics: A Tech Stack Survey

Languages, frameworks, and libraries for learning 3D graphics on Windows — with trade-offs and an opinionated learning path.

Project: cubix — Floating metallic cube with numbered faces · Reference document for stack selection

1. The Core Mental Model

Every 3D program on Windows ultimately talks to the GPU through one of four graphics APIs: Direct3D 11, Direct3D 12, OpenGL, or Vulkan. Everything else — Unity, Unreal, Three.js, Raylib, MonoGame — is a layer sitting on top of one of these. Understanding this stack hierarchy is the single most important mental model in Windows 3D graphics.

LEVEL 4 Game engines — Unity, Unreal, Godot most abstracted
LEVEL 3 Scene-graph libraries — Three.js, OpenSceneGraph  
LEVEL 2 Helper frameworks — Raylib, MonoGame, OpenTK, bgfx  
LEVEL 1 Raw graphics APIs — D3D11, D3D12, OpenGL, Vulkan closest to GPU
LEVEL 0 GPU hardware — NVIDIA, AMD, Intel drivers silicon
Key Insight The concepts of 3D (transform matrices, vertex / pixel shaders, lighting models, depth testing) are 100% portable across every stack. Only the API surface differs. So the “best” stack is whichever one lets you spend the most cognitive energy on concepts and the least on boilerplate frustration.

2. Level 1 — Raw Graphics APIs

The “learn how the GPU actually works” tier.

A. Direct3D 11 + C++ (Win32 window) Educational gold standard

What it is: Microsoft’s mature 3D API. You write HLSL shaders, manage vertex / index buffers, set render states, and present frames yourself.

Pros

  • The native Windows way. Documentation, samples, and tooling (PIX, RenderDoc, Visual Studio Graphics Debugger) are first-class.
  • Teaches the GPU pipeline directly: input assembler → vertex shader → rasterizer → pixel shader → output merger. This vocabulary applies everywhere later.
  • D3D11 is the sweet spot — modern enough to be relevant, simple enough that you don’t drown in synchronization (unlike D3D12 / Vulkan).
  • HLSL is also what Unity and Unreal use, so shader skills transfer.

Cons

  • ~300–500 lines of C++ boilerplate before you see a triangle (window creation, device / swapchain setup, shader compilation, buffer uploads).
  • Windows-only.
  • You write your own math library or bring one (DirectXMath ships with the SDK — use it).

Verdict: Best educational choice if your goal is to understand 3D graphics deeply. The path that demystifies everything else.

B. Direct3D 12 + C++

Like D3D11 but you manage GPU memory, command lists, fences, and resource barriers manually. About 2,000+ lines for a triangle. Skip unless you’re targeting AAA-game performance work. Educational ROI is poor for a learner — you spend 90% of your time on plumbing rather than on graphics concepts.

C. OpenGL + C / C++

Pros

  • Cross-platform.
  • Huge tutorial ecosystem — LearnOpenGL.com is legendary.
  • GLSL is similar to HLSL.
  • Slightly less boilerplate than D3D11.

Cons

  • Microsoft no longer pushes OpenGL on Windows; drivers are second-class compared to D3D.
  • Future is shaky — the industry is moving to Vulkan and D3D12.

Verdict: Great pedagogical choice if cross-platform matters to you. Otherwise D3D11 is more “Windows-native.”

D. Vulkan + C++

About 1,500 lines for a triangle. Designed for engine authors, not learners. Skip for this project.

3. Level 2 — Helper Frameworks

The “skip the boilerplate, keep the concepts” tier.

E. Raylib + C Recommended for fast learning

What it is: A tiny C library (~150 functions) that wraps OpenGL. DrawCube(), BeginMode3D(camera), IsKeyDown(KEY_LEFT) — that’s the API style.

Pros

  • Your cube + rotation + keyboard handling fits in roughly 80 lines of C.
  • Built-in camera, math, input, model loading, and shader support.
  • You can drop down to raw GLSL shaders for the metallic look — so you still learn shading.
  • Zero dependency hell; single-header builds work on Windows.

Cons

  • Hides the API plumbing — you won’t learn what a swapchain is.
  • Smaller ecosystem than the big engines.

Verdict: Sweet spot for “build it, understand the graphics, don’t fight Win32.”

F. MonoGame + C# XNA successor

What it is: A C# framework that started as Microsoft’s XNA (Xbox indie game framework, 2006). Cross-platform, mature, with a full content pipeline.

Pros

  • C# — strong typing, garbage collection, debugger you already know.
  • HLSL shaders, like D3D. A “real” graphics programming feel.
  • Excellent for someone who wants C# plus actual graphics knowledge.

Cons

  • More ceremony than Raylib (project templates, content pipeline).
  • Smaller community than Unity.

Verdict: Best C# option if you want to learn real graphics, not Unity scripting.

G. OpenTK + C#  /  Silk.NET + C#

Bare OpenGL / Vulkan / D3D bindings for .NET. Similar trade-offs to raw OpenGL but in C#. Use if you want C# and the educational depth of Level 1.

H. bgfx + C++

A render-API-agnostic library — your code runs on D3D11 / 12, OpenGL, Vulkan, and Metal. Used by some indie games. Steeper than Raylib, more flexible.

4. Level 3 — Scene-Graph Libraries

I. Three.js + JavaScript (in a browser) Fastest iteration

What it is: A JavaScript 3D library running on WebGL in any browser.

Pros

  • Fastest path to a result. Your cube + arrow-key rotation is roughly 50 lines of JS in a single .html file.
  • No compiler, no build system, no Windows SDK. Save and refresh.
  • Excellent docs, immense ecosystem, MIT-licensed examples for exactly your problem.
  • The lighting / shadow stage 2 requirement is a built-in feature: THREE.DirectionalLight + castShadow = true.

Cons

  • Runs in a browser, not a “real Windows app.”
  • JavaScript may feel less serious if you want to learn systems-level graphics.
  • Hides almost all the GPU internals.

Verdict: If your goal is “understand 3D scene composition” rather than “understand the GPU,” this is the most efficient learning environment — you spend brain cycles on lights, materials, cameras, and transforms instead of on Win32 message loops.

5. Level 4 — Game Engines

J. Unity + C#

Drag a cube into a scene, attach a C# script, done in 15 minutes. But: you’d learn Unity, not 3D graphics. The cube would be 5% of the work; the other 95% would be “learn the Unity editor.” Overkill for this scope.

K. Unreal + C++ / Blueprints

Same critique as Unity, only heavier. Skip.

L. Godot + GDScript / C#

Lighter than Unity, open source, but still an editor-driven workflow. Great engine, wrong tool for this learning goal.

7. Recommendation Tree

I want to deeply understand how a GPU draws a cube. Painful setup is fine. → Direct3D 11 + C++
I want to build it fast, learn graphics concepts, skip plumbing. → Raylib + C
I want C# and real graphics, no game-engine hand-holding. → MonoGame + C#
I want results today and to learn scene-graph concepts. → Three.js + JavaScript

8. Your Chosen Learning Journey

You decided to walk down the abstraction ladder — from highest-level to lowest-level — so each new stack reveals what the previous one was hiding. This is the recommended order for a graphics learner.

  1. Three.js + JavaScript — learn the scene-graph mental model: meshes, materials, cameras, lights, transforms. See results in seconds. No build step.
  2. Raylib + C — the same concepts but in C, with a tiny imperative API. Begin to feel the shape of a render loop and how vertex / pixel data is described.
  3. MonoGame + C# — same concepts in a managed language with a proper content pipeline; introduces HLSL shaders and a more “industrial” structure.
  4. Direct3D 11 + C++ — finally meet the GPU pipeline directly: device, context, swap chain, vertex buffers, input layouts, constant buffers, render targets. Everything previous layers were hiding.
Why this order works By the time you reach D3D11, you already know what a vertex buffer is — you only need to learn how Microsoft’s API expresses it. This is much easier than learning concepts and a low-level API simultaneously.

9. The Same Cube, Four Times

Each stage will produce the same visual result — a metallic cube floating in the center of the screen with digits 1–6 etched onto its faces, rotatable with the arrow keys, with optional light direction control on the a / s / d / w keys. The output is identical; the journey through the code reveals the differences.

Same problem, four lenses. The cube is the constant; the stack is the variable. That is the entire point of the exercise.
